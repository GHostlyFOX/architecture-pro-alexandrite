# Архитектурное решение по кешированию

## Мотивация

Внедрение кэширования позволит:

1. Кэширование списка заказов в MES позволит ускорить работу операторов: они смогут быстрее брать заказы в работу и оповещать клиента о статусе заказа при запросах 
2. Также кэширование заказов позволит исключить конфликты в работе между операторами (что потенциально снизит текучку кадров и неопределенности по статусу/оператору конкретных заказов), а также количество дублирующих и ненужных действий (таких, как взятие в работу уже взятого заказа)
3. При правильной настройке снизится нагрузка на БД, что ускорит другие запросы к БД и потенциально сэкономит компании деньги на аренде облачных ресурсов
4. Дополнительно, в случае введения кэширования в компоненте MES по расчету стоимости изделий, можно потенциально снизить нагрузку на MES в плане повторного расчета стоимости одинаковых изделий

## Предлагаемое решение

### Сравнение подходов

Для выбора стратегии кэширования проведено сравнение возможных подходов:

| Подход        | Применимость                           | Комментарий                                                                                                                                                                         |
|---------------|----------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Client-side   | Подходит, но для статического контента | Подходит для не меняющихся элементов интерфейса, но не подходит для списка заказов, так как пользователям (операторам) важно иметь максимально актуальные данные по статусам заказов |
| Cache-aside   | Подходит, но с низким TTL              | Наиболее легко оптимизирует чтения и с низким TTL (до 30 секунд) позволяет возвращать корректные данные                                                                             |
| Read-through  | Не подходит                            | Не подходит, так как есть высокий риск несогласованности данных по заказам                                                                                                          |
| Refresh-ahead | Не подходит                            | Возможна несогласованность при ошибках в данных                                                                                                                                     |
| Write-through | Подходит для операций записи           | Строго согласованные данные по заказам, подходит для оптимизации операций обновления статуса                                                                                        |
| Write-ahead   | Не подходит                            | Данные могут оказаться несогласованными в случае ошибок записи в БД                                                                                                                 |

### Выбор подхода

* Client-side кэширование на основе заголовков для статического контента
* Server-side кэширование с использованием Redis для всего остального: cache-aside кэширование для запросов на чтение с низким TTL (определить экспериментально), write-through для обновлений статуса заказа

### Инвалидация кэша

Для инвалидации кэша в случае работы с заказами через MES API предлагается использовать следующие стратегии:

* **Временная инвалидация**: для записей в кэше со специфическими наборами фильтров/пагинацией для конкретного оператора, не применяется к самым часто запрашиваемым страницам
* **Инвалидация по ключу**: при изменении статуса заказа - инвалидировать кэши, в которых лежит запись о данном заказе (с предыдущим и с новым статусами)
* **Инвалидация на основе изменений**: при получении нового заказа через очередь - инвалидировать кэши списков необработанных заказов

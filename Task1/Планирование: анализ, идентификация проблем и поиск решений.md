# Анализ проблем в информационных системах компании «Александрит»

## Идентификация проблем

### Бизнес-проблемы

* **Время расчета стоимости** долгое и сильно колеблется (от 2 до 30 минут, в зависимости от сложности модели)
* **Часть заказов не доходит до производства**, из-за чего клиенты могут ждать свой товар с задержками вплоть до нескольких месяцев
* **Заказы, создаваемые через API MES, долго не доходят до производства** из-за повышения нагрузки на системы компании
* **Список заказов долго грузится** в интерфейсе MES, из-за чего операторы не могут реагировать на заказы оперативно
* Цикл тестирования **замедляет скорость релизов**, причем с ростом количества заказов релизы замедляются еще сильнее

### Технические проблемы

* Сервисы компании **не масштабируемы**, из-за чего производительность компании не может быть увеличена
* Сервисы **не устойчивы к повышенной нагрузку**, что приводит к ошибкам при взаимодействии с ними как через API, так и через MQ
* Судя по всему, **отсутствуют гарантии доставки** сообщений по RabbitMQ, что может приводить к потерям заказов
* **Степень observability сервисов** либо низкая, либо отсутствует вообще, что ведет к непониманию источников проблем и узких мест

## Инициативы по исправлению

### Список инициатив

1. Внедрить или настроить мониторинг и логирование в сервисах для более точной идентификации проблем
2. Добавить механизм circuit breaker для снижения нагрузки на MES при большом количестве запросов на расчет стоимости изделий
3. Добавить кэширование запросов к MES для ускорения работы операторов и обработки заказов
4. Усовершенствовать цикл релиза: внедрить автоматические E2E-тесты, механизм feature flags для быстрого включения готовых фич, и практику выпуска hotfix для послерелизного исправления багов
5. Настроить acknowledgement при работе с RabbitMQ для гарантированной доставки сообщений, либо перейти на Kafka для межсервисного взаимодействия (требуется дополнительные исследования существующих проблем)
6. Развернуть систему в Kubernetes для масштабируемости, после чего добавить балансировщик нагрузки для перераспределения расчетов заказов

Также для внедрения всех перечисленных изменений в системы потребуется расширение штата ИТ-команды компании. Предлагается нанять:

* Как минимум 1 QA-инженера с опытом автоматизации E2E-тестов и менторинга других тестировщиков, переходящих из ручного тестирования в автоматическое. Таким образом на горизонте полугода-года в команде будет два полноценных QA с опытом автоматического тестирования, а большинство сервисов будут покрыты автотестами
* 2-3 DevOps инженеров для внедрения необходимых инфраструктурных изменений, т.к. большинство инициатив подразумевают внедрение новых инструментов. Хотя бы один из нанимаемых инженеров должен быть знаком с Kubernetes, и хотя бы один - со стеком ELK, Grafana, Prometheus и Jaeger

### Целевая архитектура

* Все сервисы и БД перенесены в кластер Kubernetes
* Сервисы (в первую очередь, MES) поддерживают горизонтальное масштабирование, имеются механизмы circuit breaker и балансировки нагрузки
* Добавлен кэш для наиболее часто выполняемых запросов к MES из интерфейса системы
* Настроен сбор логов с подключенной возможностью их анализа и поиска с помощью ELK-стека
* Настроен мониторинг целевых показателей по всей системе и по каждому сервису через Prometheus, и визуализация через Grafana
* Подключена трассировка запросов с помощью OpenTelemetry и Jaeger
* По результатам анализа межсервисного взаимодействия проведено внедрение acknowledment в RabbitMQ, либо внедрена Kafka для межсервисного взаимодействия

### Наиболее приоритетные задачи

С учетом того, что на данный момент не до конца понятны причины проблем в ИТ-сервисах, предлагается в первую очередь заняться следующими задачами:

1. Настройка *анализа логов, мониторинга и трассировки* вокруг наиболее загруженного компонента системы - MES - и выработка лучших практик для быстрого распространения на другие сервисы
2. Внедрение *кэширования частых запросов к MES*, что позволит сразу же решить одну из ключевых проблем с системой, а именно ускорится работа операторов. Как только на них снизится нагрузка, они смогут эффективнее работать и, возможно, получится временно принимать часть заказов напрямую через них, для снижения нагрузки на системы до их усовершенствования 
3. Подключение механизма *circuit breaker* для того, чтобы дополнительные запросы к MES не приводили к еще большей нагрузке к и без того нагруженному сервису 

Также после найма дополнительного QA-инженера следует немедленно приступить к автоматизации E2E-тестов.
